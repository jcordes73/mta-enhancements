The proposal — a triage store + a diff endpoint

  • Triage table keyed by the incident identity key (proposal ①) — five states, comment, author, full history table
  • Carry-over tiers: exact → silent; fuzzy (drift ≤ 10) → flagged for re-confirm; weaker → offered, never auto-applied
  • Diff endpoint: added / resolved / changed, effort delta, carry-over summary; toolchain manifests annotated
  • One mechanism, every surface: Hub UI, static report, IDE — via the kai MCP solution server, not three stores
  • One new scope (triage:write); reads ride existing analysis-read scopes

Security & test depth

  • First write surface on analysis data: enum-checked states, comment length cap, full audit, business-service guard
  • Triage is an LLM-injection surface — comments untrusted (length-capped, rendered safely); kai consumes state, not comment text, for weighting
  • Tests: tier classification incl. negative cases (vanished incidents, orphaned rules, concurrent writes, length-cap)
  • Contract: OpenAPI-validated endpoints; hub↔kai normalization agreement on the shared case vector
  • E2E: the full round-trip — triage via IDE (Playwright) → visible in Hub + static report → carries across re-analysis

Alternatives considered & rejected

  • Client-side triage, opportunistic sync — never converges; produced the divergences users already report; reports stay blind
  • Store in the kai solution server — triage must outlive any AI component; solution server consumes it (via #279), does not own it
  • File-/rule-level triage only — cannot express "this finding is real, that one is not"; insights-level triage is a possible later addition
  • Diff computed client-side from exports — N consumers, N matchers, N divergences; the Hub already owns identity

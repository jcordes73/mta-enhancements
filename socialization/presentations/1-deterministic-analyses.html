The proposal — four parts

  • Toolchain manifest — digest-pinned analyzer image, rule-bundle digests, provider versions, settings fingerprint; rendered in Hub, CLI, static report
  • Deterministic ordering — defined sort key, stable tiebreak, no timestamps/UUIDs in result payloads
  • Incident identity key — one hash, computable by Hub, kai, and CLI; carries triage across runs
  • --strict + nightly gate — fail instead of silently degrading; seven consecutive zero-diff double-runs required for release

Risks & mitigations (honest list)

  • Strict mode breaks best-effort pipelines — opt-in per profile, default unchanged, error names the missing input
  • Ordering is breaking for positional diff tooling — consumers switch to identity-keyed diffs; transition is noisy once
  • The key freezes into the data model — schemaVersion field exists precisely because of this; hence the open questions
  • The gate has teeth — 7 zero-diff nights can hold a release for a variance bug that previously shipped unnoticed. That is the point

Alternatives considered & rejected

  • Post-hoc normalization (sort/dedupe in the Hub) — hides variance instead of eliminating it; CLI, IDE, kai still see the drift
  • Timestamp in the key — makes every incident unique per run; exactly the churn we are removing
  • Content-hash-only identity — different rules flag the same code constantly; collisions
  • Analyzer-emitted key only — possibly better long-term; deferred to an open question (couples key to analyzer release cycle)
  • Do nothing, document instability — MTA-7445-class reports recur in every large deployment; the downstream family is blocked without this

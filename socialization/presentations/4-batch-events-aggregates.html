The problem: automation by workaround

  • Bulk exists only for tags and tickets — onboarding 100+ applications means 100+ calls
  • No outbound events anywhere in the 143-path spec — every CI integration is a polling loop
  • Aggregates computed client-side — dashboards disagree with the UI, N+1 fetches, no caching
  • /tags/{id}/applications is a 404 — even the API cannot answer "what uses this tag?"
  • Upstream's own first step: server-side filter chips on Runs pages (MTA-7482 / tackle2-ui#3523)

What users would get (stories)

  • The onboarding engineer imports 120 apps and starts analysis on all of them with one call — one taskgroup, one watcher
  • The DevOps engineer registers analysis.completed — provisioning starts in seconds, not at the next poll; a fraction of the API load
  • The dashboard builder calls /report/effort?groupBy=businessService — one request, one definition, numbers that match the UI
  • The admin returns from an outage, replays the failed deliveries from the log — no events silently lost, no backfill scripts
  • The tag curator finds zero-application tags (cleanup candidates) and load-bearing ones (do not touch) in two queries

Webhooks — deliberately the smallest viable system

Webhook: url (https, SSRF-guarded), secretRef (write-only), events[]: task.completed | analysis.completed | triage.changed | application.changed WebhookDelivery: status, attempts, responseCode, durationMs v1 semantics: ONE attempt, full log, manual replay. at-most-once — honest, auditable, small. backoff = additive v2. payloads are metadata-only: IDs, states, timestamps — never code. HMAC-SHA256 + timestamp header defeats replay.

Aggregates & batch — the details that matter

  • groupBy ∈ {archetype, businessService, wave, tagCategory}, filters mirroring the UI's application filters
  • Parity acceptance test: the endpoint and the UI rollup must match on a fixture portfolio — one definition of "effort by wave"
  • SQL aggregation + indexes; NFR p95 ≤ 500 ms at 1,000 applications / 10,000 analyses — 8× the largest surveyed fleet
  • Batch: mixed success is per-application (a bad app never poisons the batch); overshooting the cap rejects whole, never truncates
  • Idempotent analysis batch: one taskgroup regardless of retries with the same parameters

Risks & alternatives (honest lists)

  • At-most-once can surprise — documented semantics, visible failed-delivery state, log + replay as the recovery path
  • Batch is an amplification surface — caps, per-op scope checks, and the observability work's queue metrics make flooding visible instantly
  • Webhooks are forever — payload schema, signature scheme, and event set become compatibility surfaces; smallest-viable v1 bounds it
  • Rejected: SSE (bigger surface for the same events), Kafka (new deployment dependency), materialized rollup store (stale-number problem), generic subscription language (extensibility wave's problem)

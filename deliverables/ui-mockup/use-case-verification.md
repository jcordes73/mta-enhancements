# Use-Case Verification — `deliverables/ui-mockup/index.html`

**Scope:** the clickable PatternFly 6 mock of the proposed MTA console improvements.
**Baseline:** `deliverables/ui-mockup/index.html` as of November 2026 (post IA consolidation).
**Reference catalog:** [`evidence/mta-improvement-suggestions.md`](../../evidence/mta-improvement-suggestions.md) — suggestion numbers `#N` below cite it; the mock renders the same numbers as annotation badges — hidden by default (user request: inline badges otherwise widen buttons and wrap column headers), revealed by the masthead **Annotations** switch or `#anno=1` in the URL; the per-screen "Suggestions" index button works in both modes

## 1. Purpose, method, and metrics

This document walks the mock's implemented flows as **use cases per persona** (the mock's own IA
principle, #36: nav items are entities and daily workflows; everything else is tabs, drawers,
modals, or saved views). For each use case it records the verification status **and four product
metrics**:

| Field | Meaning |
|---|---|
| **Steps** | concrete reproduction path in the mock |
| **Expected** | the behavior the underlying suggestions require |
| **Suggestions** | which catalog items the flow exercises |
| **Status** | ✅ verified (automated) · 👁 verified (manual review) · ⚠ partial / mock-only |
| **Achievable** | **Y** — the journey can be walked end-to-end in the mock · **Y\*** — navigable and fully presented, but the concluding action is intentionally inert (the mock presents the surface; it does not change state) · **N** — cannot be walked |
| **Clicks** | interactions (clicks; Enter = 1) from mock boot to the state that fulfills the use case. Boot persona is **architect**, boot screen is **Home**; journeys in another persona's landing include the persona-switch click. Measures navigation cost — the "#36/#41: one click to the work" claim. |
| **Data complete** | **Full** — everything needed to act on the use case is presented · **Partial** — presented with gaps (top-N samples, missing editors, inert concluding actions) |
| **Data quality** | **High** — internally consistent across surfaces (counts, dates, IDs reconcile; dates coherent with "today") · **Medium** — minor inconsistencies or sample-scale simplifications, documented per row |

**How it was verified.** Two harnesses were used, both against the real PatternFly 6.7.0 stylesheet:

1. **Automated (jsdom):** loads `index.html`, drives clicks and hash changes programmatically,
   asserts DOM state (modal visibility, filter results, tab panels, chip rendering, ARIA state).
   Covers behavior, not layout.
2. **Automated (headless Chrome):** same assertions plus *computed layout* (rendered heights,
   `display` values) — catches what jsdom cannot, e.g. PF6 CSS states like `:not(.pf-m-expanded)`.
3. **Automated (dead-end audit):** a DOM walk over every screen, modal, and drawer template that
   finds *entity references rendered as plain text* — application names, archetype names, rule
   paths, tracker keys — and checks whether the reference is clickable or a dead-end. Wired
   references are then click-tested (including `stopPropagation` inside clickable rows, so the
   reference navigates to *its* target while the row still opens the row's own view). The same
   audit covers the **navigation chrome**: every tab (16) is clicked and its panel asserted
   visible, every nav item (6) and wizard step (5) is click-tested to its target, and every
   pagination control is either wired (Applications) or fully `disabled` (static samples). It also
   runs **at runtime**: every drawer/modal variant is opened (all 12 app-drawer states, the seven
   side drawers, the comparison view) and every rendered table row is checked for clickability —
   catching content assembled by JavaScript that a static template scan would miss.

The jsdom suites themselves live in the workspace at [`verify/`](verify) — 19 suites plus the
shared `inv-rows-reference-wp3.json` fixture, with a per-suite index, run instructions, and the
full list of jsdom limits in [`verify/README.md`](verify/README.md). They resolve jsdom via
`require('jsdom')` (after `npm install` inside `verify/`) with a fallback to the historical
ephemeral `/tmp/node_modules` location. The §4 defect-log rows below cite `/tmp/opencode/`
paths as they were recorded at the time; the current canonical location is `verify/`.

> ⚠ Known harness limitation: jsdom does not execute inline `onclick` handlers on content cloned
> from `<template>` elements. That is a jsdom gap, not a mock defect — real browsers execute them
> (confirmed with a minimal repro). All template-originated flows were therefore verified via
> headless Chrome or attribute inspection.
>
> ⚠ Harness note (drawer investigation, 2026-11-12): clicking the invoicing row appeared to "not
> open the drawer" in both harnesses. Root cause was in the test, not the mock — twice over:
> (a) `app2` is in the mock's `MODAL_VIEWS` set, so the row routes to the application detail
> **modal** (`#modalApp`), while the harness asserted on the side-drawer elements (`#drawerRoot`/
> `#drawerBody`); asserting on `#modalApp` shows the click works in jsdom and Chrome alike.
> (b) jsdom additionally fires a `hashchange` → `applyHash` → `show()` round-trip on drawer opens
> that real browsers don't reproduce, so *any* drawer-state assertion made synchronously in jsdom
> is timing-dependent — drawer paths are Chrome-verified only. Separately, a jsdom-only ordering
> artifact means drawer opens via row click must be asserted after the hashchange settles. No
> product change resulted from this investigation; a similar false alarm was pre-empted for the
> default `wave3` filter chip, which is statically `on` at boot (a new unassigned app is hidden
> until the chip is cleared — same as upstream, where an active filter hides new rows).

## 2. Persona journeys

### 2.0 RBAC — how the personas are enforced (user request)

Personas are not cosmetic: a `resource:verb` scope model (`RBAC` in the source) drives **navigation,
deep links, and in-page verbs**. `admin` holds every scope; work personas get the narrow set their
job needs.

**Screen visibility (views list per persona):**

- **architect** — Home, Applications, Incidents, Waves, Reports, Agentic, Import wizard
- **pm** — Home, Applications, Incidents, Waves, Reports, Task manager
- **pgm** — the same read-only view set as pm (the difference is tenancy scope — below and §2.0.1)
- **migrator** — Home, Applications, Incidents, Waves, Agentic, Task manager, Import wizard
- **admin** — everything, plus the Administration hub · **padmin** — the same views (UC-X17)

**Who sees Reports, and why** (user question "who should be able to see reports?"): five of the six
personas — architect, pm, pgm, admin, padmin; the **migrator does not**. The rationale: the
migrator's surfaces are *queues and records* (Agentic run tables, Task manager, Incidents) — its own
runs' state, event logs, and cost accounting live on the run record itself, while Reports aggregates
(showback, trends, risk rollups) answer portfolio questions for the people who own the portfolio.
The deep-link guard (`#scr=reports` as migrator → Home + toast) is pinned in the RBAC suite. The
question also exposed that Reports → Agent runs was the one report surface not tenancy-clamped
(static KPIs contradicting the records) — now the whole tab computes from the scoped store (UC-X16).

**Tenancy scope — Project manager vs Program manager vs Migrator (#41):** the Project manager and
the Program manager share the same read-only view set but differ in *tenancy scope* — the **Project
manager** belongs to a team (Claims) and is **locked to it** (the masthead 🏢 switcher disables with
a tooltip pointing at the Program manager persona; `&org=`/`&team=` deep-link params lose to the
lock), while the **Program manager** keeps the free organization/department scope and additionally
sees the **cross-team coordination view** on Migration waves (§2.0.1) plus a program-item in the
notification feed. The **Migrator is team-locked too** (same home team, Claims): it keeps its
execution verbs (applications CRUD, incident triage/resolve, run creation, task cancel) but
exercises them within the team that owns the applications — the lock works exactly like the Project
manager's (switcher disabled with a tooltip, deep-link params lose).

**Credential governance (#15 + #41, user request):** credentials are **team-owned resources** —
every credential belongs to exactly one team (the team whose repositories consume it), the same
ownership invariant as applications — and management follows the tenancy clamp: the **architect and
migrator** hold `identities:create / edit / verify / delete` for *their team's* credentials, the
**admin personas** for the whole organization (platform admin: cross-org, audited); pm/pgm hold
none.

**Credentials is a first-class view** (promoted out of the Administration hub — the WP6 "the hub
holds configuration, not operations" precedent): `scopedCreds()` is the only credential-list source,
the table shows the current scope's credentials with an **Owner team** column, `#scr=credentials`
and the legacy `#scr=config&tab=credentials` both land there, and the hub retains 8 tabs.

**Readiness is a wave GATE condition, not a separate card** (user challenge "do we really need a
pre-wave check card on Migration waves?" — answered: the *check* yes, the *card* no): credential
readiness appears in the wave's **Gate status** list (#46 definition-of-done) — Wave 3 names the
expiring `svn-read-key` and the Wave-3 members it serves, and notes the unverified credential is
*unassigned* (no gate impact) — visible to **everyone gating the wave** (gate *state*, not
credential *management*: no secrets, no verbs; management stays `identities:*` on the Credentials
view). The data settled the argument: the card's headline failure (unverified `nexus-mvn`) gated
nothing (used by 0 applications), while the real Wave-3 risk — an expiring credential used by two
members — read as one static table row among three.

**Assignment at creation (#15 + #41):** the application form's **Source credential** select offers
exactly the *selected team's* credentials (it repopulates when the Team select changes; a team
without credentials gets a guided none-option), edit preselects the assigned credential, the
application detail names it (both the parameterized and the canonical template paths follow
reassignments), and the "Used by" counts on the Credentials view recompute from the assignments —
so creating an app with a credential updates the blast radius everywhere. The import wizard's
Credentials step (#44/R2-15) offers the owning team's credentials, filtered to the scheme's kinds.

**Verb summary** (full matrix below): **architect** = applications CRUD + queue analysis, wave
re-validation (`waves:edit`), review sign-off (`review:write`), agent-run creation (`runs:create`)
and cancellation of running runs (`runs:cancel`), credential management within the tenancy clamp
(`identities:*`) · **pm** = none (read-only by design) · **migrator** = applications CRUD + queue
analysis, incident triage/resolve, agent-run creation, **cancellation of running runs**
(`runs:cancel` — the executor can stop a run that is burning quota or gate time, user request),
task cancel, credential management within the team (`identities:*`) · **admin** = `*`.

**Enforcement:** nav links and the masthead task shortcut hide per view list; gated buttons disable
with the missing scope on hover; deep links to disallowed screens redirect Home with a warning
toast; the notification feed (#36 item 5) filters to the active role (its masthead bell renders as
a fa-bell icon + unread badge per user request — it previously rendered as a bare badge with no
icon).

**Related sections:** **Admin tiers (#41/#42, user request)** — the **Admin** is an *organization*
admin, org-locked like every other persona (the 🏢 switcher's organization entries disable; `&org=`
deep links lose to the lock; the Teams table shows only its own organization), while the **Platform
administrator** (`padmin`) operates *above* the tenancy model (UC-X17) — detailed in §2.0.2.
**Architect responsibility levels (#41 + #36, user request)** — the architect additionally carries a
**responsibility level** (application / team / department / organization) that clamps the tenancy
scope (UC-X18) — detailed in §2.0.3.

Verified by `verify/verify-rbac.js` (171 checks).

### 2.0.1 Multi-tenancy — organizations, departments, teams (#41, user request)

The scope model (`TENANCY` in the source) implements the user's definition: **organizations are
isolated** — switching one changes every application, wave, and aggregate you can see — each
organization has **departments**, departments have **teams**, every application belongs to
**exactly one team** (a team may own many), and a team is staffed with **architects, project
managers, and migrators**.

**How the scope drives the UI:** `state.org/dept/team` is the scope: the masthead switcher
(🏢 Northwind Financial · Retail Banking · all teams) opens one cascading org → department → team
menu with member counts; `scopedApps()` is the only application-list source, so team scope filters
the Applications rows and the wave membership/effort/risk aggregates cascade automatically. Deep
links carry the scope (`&org=&dept=&team=`).

**Waves belong to organizations:** Waves 1–4 are Northwind-owned — other organizations see a guided
empty state (#43) pointing at the wave-assignment path, and Home/Reports carry a "data scope" note.

**Teams management (Administration → Controls):** a **Teams** management table (the hierarchy with
the three role columns and live application counts) with `teams:create`/`teams:delete` admin-only
and the established guarded delete — a team with assigned applications cannot be deleted; the block
reason names the count and the exactly-one-team invariant. The app form's Team select (grouped by
department) enforces exactly-one-team on create and edit.

**The persona × tenancy intersection (user request):** the **Project manager** and **Migrator**
personas are locked to their home team (Claims — switcher disabled with a tooltip, deep-link scope
params lose to the lock); the **Program manager** persona keeps free org/department scope and gets
the **cross-team coordination info rendered in each wave** (user request "move the coordination
info into each wave" — the separate pgm-only card duplicated the wave's own context one section
away and is gone): each wave's detail opens with its coordination strip — contributing teams with a
Cross-team flag when the wave spans more than one team (sampled: Wave 4 = Claims + Portfolio +
Customer digital), the wave's own quota blockers (#38) naming the teams they hit, and the wave's
side of the inter-wave dependency edge with its team-boundary verdict (Wave 3: edge out, stays
within Claims; Wave 4: edge in) — while a team-scoped Project manager sees no strips (the info
names other teams by definition). The **program landing on Home keeps the summary** (teams in
scope / cross-team waves / shared blockers KPIs), a program item in the notification feed, and its
own guided tour.

**Sampled data:** Northwind Financial keeps the 12 original apps (byte-equality preserved);
Meridian Health adds 3 isolated apps (patient-records, lab-results, appointment-api).

Verified by `verify/verify-tenancy.js` (49 checks).

### 2.0.2 Admin tiers — organization admin vs platform administrator (#41 + #42, user request)

Admin is split so the isolation invariant holds for every persona inside a tenant, with exactly one
explicit, audited way across it:

- **Admin = organization admin (tenant-side).** Same capabilities as before, but scoped to *its*
  organization: the 🏢 switcher's organization entries render disabled (departments and teams remain
  selectable), `&org=` deep-link params lose to the lock, `setOrg` is a guarded no-op, and the
  Controls → Teams table lists only the current organization's teams. Nothing about the admin
  persona pierces another tenant anymore. Its **Home landing answers an organization question** —
  "Is my organization's migration on track?" — not a platform one: the original "Is the platform
  healthy?" landing (static queue-depth/failed-tasks/verification KPIs + a Platform-health card)
  predated the admin-tier split, and the platform framing moved to the platform admin's
  tenant-portfolio landing above. The rebuilt landing is **org-scoped and live** (`scopedApps()` IS
  its organization): applications, wave-assigned, open incidents, agent spend (#20), expiring
  credentials (#15), plus an Organization-status list with deep links (failing Wave-3 gate, risk
  distribution, credentials, task queue) — refreshed on tenancy/CRUD changes, and stable under the
  guarded `setOrg` (Chrome shotOA).
- **Platform administrator (`padmin`) = operator-side, above tenancy.** The only persona with
  `tenants:*` verbs (`can('…','tenants')` is exclusive to it, so `scopes: '*'` no longer implies
  them). It gets: a **tenant-portfolio Home landing** (user question "what could be useful on the
  home screen for a platform admin?" — its tour question "Which organizations need attention?"
  previously had no landing at all, only a tour routed to Controls; a follow-up request added the
  **platform-health section** the org-admin reframe had removed — now fleet-wide where it
  belongs): tenancy-footprint KPIs
  (organizations / teams / applications, live from the `TENANCY` store), a **per-organization
  status table with an attention verdict** (apps, wave-assigned, fleet-wide agent spend #20 —
  computed above the clamp on purpose, expiring credentials #15, and a verdict: expiring
  credentials → onboarding → healthy), a **Platform-health
  section** (analysis pipeline, tracker sync #37, fleet-wide credential health #15 computed live
  across all organizations — each org admin sees only its own — plus queue-depth #30, failed-tasks
  #3/#38, and verification-pass-rate #47 KPIs), the **cross-tenant audit trail up front** (#42 —
  this persona's own accountability surface), and a `tenants:create` **Provision organization**
  shortcut; the orgs table, the audit trail, and this landing share one renderer, so provisioning
  and audit entries refresh all three (the 4th tour step now leads with it). Plus: the
  **Organizations** sub-tab in Administration → Controls (org table with
  department/team/application counts + **Add organization** provisioning modal with required-name,
  duplicate, and required-first-department validation), the **cross-tenant audit trail** (#42:
  time, actor, action, target — seeded with the Meridian provisioning entry), a program item in the
  notification feed, a 4-step guided tour, and cross-org movement: switching organization works
  only for this persona and each pivot appends a `tenant:access` audit entry *and* raises a warning
  toast naming the tenant — cross-org reads are deliberate and recorded, never ambient. Deep links
  with `&org=` also audit for this persona.

Verified by `verify/verify-rbac.js` (the "admin tiers" block) and the org-lock deep-link
checks in `verify/verify-tenancy.js`.

### 2.0.3 Architect responsibility levels — application · team · department · organization (#41 + #36, user request)

The architect is not one free-roaming role: an architect is **responsible for a scope**, in four
levels. A 📎 **Responsibility** selector renders in the masthead (beside the 🏢 switcher) **only
while the Architect persona is active**:

- **Application architect** — responsible for one application (sampled: `payments-api`); sees only
  its row, its analysis, its incidents, and its wave lane (Wave 3) — the tenancy switcher disables
  with a tooltip pointing at the responsibility level as the way out, and the masthead scope label
  gains an `· app payments-api` suffix.
- **Team architect** — responsible for one team (Claims): the team's 6 applications and their wave
  lanes; the switcher disables (same lock pattern as the Project manager/Migrator).
- **Department architect** — responsible for one department (Retail Banking): the department is
  locked (`setDept` to another department is a guarded no-op and the menu renders the other
  department disabled), but **teams remain selectable** within it.
- **Organization architect** (default, boot state) — responsible for the whole organization: the
  organization is locked (like the admin; `setOrg` to another organization is a no-op and Meridian
  renders disabled in the menu), departments and teams remain selectable.

The level is a **clamp, not a separate dataset**: it narrows what the existing tenancy engine may
select (`archClampScope()`), and every surface — Applications rows, wave lanes, aggregates, Home
KPIs, Reports — follows through `scopedApps()` as usual. Lowering the level locks further
(app/team engage the team lock); raising it keeps the current position but re-enables movement
(widening is explicit). The level is deep-linkable with `&arch=app|team|dept|org`; deep-link
`&org=` params still lose to the architect's organization clamp. Each level explains itself: the
selector's menu note (#41 + #36) and the per-item descriptions name the responsibility and what
visibility it grants.

Verified by `verify/verify-rbac.js` (the "architect responsibility levels" block: selector
visibility per persona, dept no-op with teams free, team lock, app single-row + W3-only lane,
deep-link clamp, level-switch switcher refresh) + Chrome screenshot (open Responsibility menu).

## 5. Data-quality findings (summary of the per-row grades)
The mock's data holds up well where it matters most — **cross-surface consistency** — with the
findings below from grading the per-row data quality (two deliberate simplifications, plus
defects found and fixed along the way):

1. **Sample portfolio vs. story counts.** The inventory is a 12-row sample, while cards and
   matrices tell a portfolio-scale story ("Claims (12 apps)", "18 of 100+", cohort "18 members").
   Within the sample the numbers reconcile (6 Claims rows; cust-portal's 137 incidents / 890 pts
   consistent from table → drawer → diff view); across scales they intentionally do not. The wave
   membership card reconciles three ways (inventory `data-wave`, ticket table, timeline edge).
   *Recommendation for demos: say "sample inventory, full-portfolio numbers" up front.*
2. **Decorative filters: fixed.** Two filter surfaces originally changed state without filtering
   rows — the Incidents State menu (defect #9) and the Administration → Tasks Application/Age
   toggles (defect #11). Both are now fully functional: they filter rows, combine with their
   filter chips, and show a guided empty state (#43). All ten Applications filters, both Incidents
   filters, both Tasks filters, and the Trends run-picker hand-off are affordances-with-function;
   the mock has none left.
3. **Top-N honesty.** Where data is sampled (incident groups "top 3 of 137", affected apps "top 4
   of 18", agent runs "1–3 of 16") the sampling is labeled in the UI rather than hidden. The same
   applies to dependency inventories: payments-api (5 of 214 artifacts) and invoicing (2) are the
   sampled examples, and apps without sampled data say so and hand off to the Dependencies view
   instead of showing an empty table.
4. **Detail identity follows the clicked row.** The incident detail's story scaffolding (rule
   transparency, hint verification, triage history, role-gated verbs) is one canonical pattern,
   but its identity fields — application, incident, effort, triage state, tracker outcome, rule
   path — are now assembled from the clicked row, the same pattern the app drawer already used
   (#33 item 8). Before this (defect #14), every incident row opened the canonical invoicing
   story regardless of which application's row was clicked.
5. **Reference integrity: two accepted classes of dead-ends.** The dead-end audit (defects #10
   and #12) wired every entity reference that has a correct in-mock target — including the
   runtime-generated rows the static scan initially missed. What intentionally remains plain text:
   **tracker keys (MIG-412/418/425)** — they reference an external system, and the only in-mock
   ticket drawer holds MIG-425's failure story; pointing the others at it would present wrong
   data (the real product would deep-link to the tracker, #37); **read-only record rows** —
   triage audit-log entries (#33 item 1: the trail is for reading, not navigating), ticket
   attempt history, agent token-accounting and policy rows, which are records rather than
   references; **self-references** (drawer and modal titles, artifact tables in the Dependencies
   views, the Rule-coverage tab's own rule path, YAML/OpenAPI excerpts); **references with an
   adjacent way out** (the Reports provenance cell names the archetype beside a "view group
   assessment" link; the incident modal's cohort line beside "open cohort"); and **workflow scope
   labels** (`archetype: payments-api` tags, which are metadata, consistent with filter chips not
   being navigation).
6. **Column alignment is presentation, but misalignment reads as wrong data.** The Applications
   table's header was missing the checkbox column's `<th>` (defect #16), so every label sat one
   column left — most misleadingly, "Effort #4" sat over the Analysis cell, whose "Running 61% ·
   23 incidents" reads like a status. The underlying data was never wrong, but a header that
   mislabels its column destroys trust in the numbers beneath it as effectively as a data error.
   Fixed and geometry-verified (left-edge deltas ≤ 4px); every other checkbox table in the mock
   was swept for the same mismatch — none found.
